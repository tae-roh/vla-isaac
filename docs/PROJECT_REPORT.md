## 0. 최종 결과

동일 조건(`eval_base` 홀드아웃, greedy 디코딩, 300스텝 예산)에서 측정한 최종 성공률.

| 단계 | 체크포인트 | 에피소드 | 성공률 |
|---|---|---|---|
| 사전학습 베이스 | `openvla/openvla-7b` | 64 | **0.0 %** (0/64) |
| SFT | 20,000 스텝 | 352 | **15.6 %** |
| SFT + RFT | GRPO 105 스텝 | 352 | **19.9 %** |

**SFT 는 명확히 기여했다.** 베이스 0/64 는 95% 상한이 약 4.7%(rule of three)이고
SFT 15.6% 는 그 상한의 3배를 넘는다. 사전학습 정책은 이 씬·이 제어 규약에서
태스크를 한 번도 완수하지 못했고, SFT 가 그것을 성립시켰다.

**RFT 의 +4.3%p 는 통계적으로 유의하지 않다.** 두 비율 차의 표준오차가 2.88%p 라
차이는 **1.48 SE** 에 그친다 (유의하려면 약 2 SE 필요). 95% 신뢰구간이 0 을 포함하므로
"RFT 가 성능을 올렸다" 고 주장할 근거가 아직 없다 — 이는 이 프로젝트의 결론 중
하나이며, §6 에서 다룬다.

> 조건당 352 에피소드는 각각 약 35분이 걸렸다. 이 크기의 차이를 유의하게 판정하려면
> 조건당 약 650 에피소드가 필요하다.

## 1. 태스크 및 스펙 정의

모든 관측·액션 스펙은 `configs/vla_spec.py` 한 파일에 모았다 (SSOT). Isaac Lab 환경
코드, SFT 실행 스크립트, RFT 어댑터가 **전부 이 파일만 읽는다.** SFT 와 RFT 사이의
스펙 불일치(뷰/proprio/정규화 규약)는 "원인불명 성능 붕괴"로만 드러나는 종류의
버그라, 구조적으로 막는 쪽을 택했다.

### 설계 원칙 — LIBERO 스펙에 정확히 맞춘다

openvla-oft 의 `constants.py` 는 실행 커맨드에 `libero` 가 있으면 LIBERO 상수셋
(`ACTION_DIM=7`, `PROPRIO_DIM=8`, `NUM_ACTIONS_CHUNK=8`, `BOUNDS_Q99`)을 고른다.
Isaac Lab 태스크를 이 숫자에 맞추면 **openvla-oft 와 SimpleVLA-RL 의 모델 코드를
한 줄도 고치지 않아도 된다.**

| 항목 | 값 | 비고 |
|---|---|---|
| 로봇 | Franka Emika Panda (`FRANKA_PANDA_HIGH_PD_CFG`) | LIBERO 와 동일 몸체 → 7차원의 *의미*까지 일치 |
| 제어 | `ik_rel_pose_dls`, 로봇 베이스 프레임, scale 0.5 | DifferentialIKController, 상대 포즈 |
| 액션 | 7차원 `[dx,dy,dz,drx,dry,drz,gripper]` | 그리퍼 이진 ±1 |
| 액션 청크 | 8 | parallel decoding (§3) |
| 관측 | `table_cam` 224×224×3 RGB **1장** | proprio 미사용 |
| 제어 주기 | **8 Hz** (`DECIMATION=15`, sim 120Hz) | §2-3 |
| 에피소드 예산 | 300 스텝 (37.5초) | |
| 정규화 | `bounds_q99` | 체크포인트 내장 `norm_stats["vla_pick"]` |

`HIGH_PD` 프리셋이 필수다 — 기본 게인(stiffness 80 / damping 4)으로는 태스크공간 IK
제어가 목표 포즈를 추종하지 못한다.

### 씬과 성공 조건

블록 3개(60×30×30 mm, red/blue/green)가 20×20 cm 영역에 무작위 배치되고, 지시문
`"put the {red|blue|green} block into the tray"` 가 타깃을 지정한다. 트레이는 로봇
베이스 기준 (0.45, 0.22) 에 고정.

성공 판정은 다음을 **전부** 만족한 상태가 **16스텝(2초) 연속** 유지될 때:

- 블록 네 모서리가 트레이 내부 (중심 높이가 아니라 코너 기준)
- 선속도 < 0.03 m/s (안착)
- **파지·리프트 이력 필수** — 끌어서 밀어넣기 차단

> **태스크 완화 이력 (보고 시 반드시 명시할 조건).** 진입률이 0 에서 뜨지 않아
> `TRAY_DEPTH` 20→10 mm, `LIFT_HEIGHT_THRESHOLD` 60→22 mm, `TRAY_INNER_SIZE`
> 1.2→2.0× 로 완화했다. 앞 둘은 근거가 있다(60mm 는 이미 제거된 박스 벽 기준이라
> 무의미했고, 20mm 레일은 정책의 리프트 높이로 물리적으로 넘을 수 없었다).
> 세 번째는 순수 완화이며, 트레이 **형상을 눈에 보이게 바꾸므로** 학습 데이터 대비
> OOD 를 유발한다. 남은 부채다.

### 2-2. `action_noise` 가 수율을 지배했다

`SubTaskConfig.action_noise` 를 0.03(Isaac Lab Franka stack 레퍼런스 값)에서 0.003 으로
낮추자 수율이 **7.1% → 45%** 로 뛰었다. 텔레옵 감도를 0.02 로 낮춰 정밀도를 얻은
탓에 우리 데모의 액션이 곱고(평균 크기 0.0037), 0.03 노이즈가 신호를 통째로 덮고
있었다.

| | 스텝간 변화 | 움직이는 구간의 방향 반전 |
|---|---|---|
| 사람 데모 | 0.1 mm | 4.8% |
| 생성 (noise 0.03) | 17.7 mm | 76.9% |
| 생성 (noise 0.003) | 2.4 mm | 47.9% |

상류도 태스크마다 값이 다르다 (Franka stack 0.03 / AgiBot 0.01 / G1 0.003) —
레퍼런스 값을 그대로 쓰면 안 되는 파라미터다.

### 2-3. 24Hz → 8Hz 시간축 다운샘플

`--inspect` 가 **모든 데모가 300스텝 예산의 1.6~2.4배**(평균 598스텝)라고 경고했다.
텔레옵 감도를 낮춘 대가로 사람 데모가 길어졌고 증강이 그 길이를 물려받았다.

24Hz 는 VLA 학습 데이터로 높은 편이다 (OXE 3~15Hz, LIBERO 20Hz). 스텝당 평균 이동이
2mm 남짓이라 인접 프레임이 거의 같았다 — **정보량 대비 프레임이 과했다.** 재수집
대신 3배 솎아 8Hz 로 낮췄다.

| | 24Hz | 8Hz |
|---|---|---|
| 궤적 길이 | 598스텝 (예산 초과) | **202스텝** (1,500개 전부 예산 안) |
| 총 프레임 | 897,712 | 298,776 |
| SFT 에폭 | 0.36 | **1.07** |
| 액션 청크 8 커버 | 0.33초 | **1.0초** (OXE/LIBERO 범위) |

두 가지가 까다로웠다:

- **액션은 델타 포즈라 k번째만 남기면 안 된다** — 구간 델타를 합산해야 한다.
  검증: 누적 이동이 오차 4e-6 으로 보존, RLDS 의 action q99 가 24Hz 대비 2.98~3.00배
  (3스텝 합산이니 3배가 정답).
- **그리퍼는 이진이라 합산 대신 구간 마지막 값**을 쓴다. 300 에피소드 측정에서
  전환 보존율 **100.0%**, 한 창에 2회 이상 전환된 창 **0 / 59,336**, 닫힘 시간 비율
  편차 0.24%p. 물리 그리퍼가 125ms 안에 두 번 상태를 바꿀 일이 없기 때문이다.

> ⚠ 환경도 8Hz 로 맞춰야 한다 (`DECIMATION=15`). 안 맞추면 8Hz 용 델타가 24Hz 에
> 적용돼 3배 빠르게 움직이고, 증상은 "성공률 0" 하나로만 나타난다.

### 2-5. 미해결 — SkillGen 0%

MimicGen 43% 인데 SkillGen 은 어떤 조건에서도 **0%** 다. 상류 버그 2개를 고쳐
구동까지는 시켰으나(`patches/isaaclab-annotate-start-signals.patch`), **두 번째
플래닝(운반 구간)이 20시도 20실패**한다. 첫 번째(접근)는 30/30 성공한다.

기각된 가설 셋 — 전부 결과를 바꾸지 못했다: 부착 물체 충돌 제외 / 로봇·블록 정적

하나도 없어 이 경로는 상류에서 검증된 적이 없다. MimicGen 으로 우회했다.

## 3. Phase 2 — SFT (Supervised Fine-Tuning)

### 3-1. 알고리즘 및 결정적 설계 선택

**OpenVLA-OFT** 레시피(parallel decoding + action chunking k=8)를 따르되, 액션 헤드에
관해 하나를 바꿨다.

```
--use_l1_regression False      # 기본값 True
```

기본값 True 면 연속 L1 회귀 헤드가 붙는다. 그건 **결정론적이라 log π 가 정의되지
않아 RL 을 붙일 수 없다.** GRPO 의 중요도비 π_new/π_old 를 계산하려면 이산 액션 토큰
+ cross-entropy 여야 한다. **이 한 줄이 이 프로젝트에서 SFT 를 하는 이유의 절반이다.**

이 설정이 곧 SimpleVLA-RL(arXiv:2509.09674) 이 요구하는 SFT 와 같다 — 논문이 밝힌
공식 OFT 대비 유일한 모델 변경이 "LLaMA2 output head + cross-entropy" 이고, 그건
공식 `finetune.py` 의 `if not (use_l1_regression or use_diffusion)` 분기와 같다.

산출물 검증도 자동화했다: 체크포인트에 `action_head*.pt` 가 있으면 즉시 실패시킨다.
하룻밤을 태운 뒤 RFT 단계에서야 알게 되는 것을 막는 가드다.

### 3-2. 학습 설정

| 항목 | 값 | 근거 |
|---|---|---|
| 베이스 | `openvla/openvla-7b` | OXE 사전학습, Franka 비중 큼 |
| 방식 | **LoRA** r=32 | |
| 배치 | 16 (grad accum 1) | |
| 학습률 | 5e-4 | OFT LIBERO 레시피 |
| LR 감쇠 | 13,333 스텝에서 10배 | OFT 는 150k 중 100k(2/3 지점) — **같은 비율로 환산** |
| 최대 스텝 | 20,000 | 약 1.07 에폭 |
| 이미지 증강 | ON | |
| proprio / FiLM | OFF | |
| 저장 | 2,500 스텝마다, LoRA 병합 포함 | |
| 하드웨어 | H100 1장 (Isaac Sim 미설치 → RT 코어 불필요) | |

> `--num_steps_before_decay` 를 넘기지 않으면 기본값 100,000 이 쓰이는데 `max_steps`
> 가 그보다 작아 **감쇠가 한 번도 일어나지 않는다.** 에러가 아니라 "레시피의 절반만
> 재현"으로 조용히 끝나는 종류의 누락이라 스크립트에 명시적으로 넣었다.

또 하나의 함정: openvla-oft 의 `detect_robot_platform()` 은 **`sys.argv` 전체를
이어붙인 문자열**에 `libero`/`aloha`/`bridge` 가 있는지로 상수셋을 고른다. 저장소를
`~/bridge/` 아래 두기만 해도 BRIDGE 상수셋이 잡혀 학습 차원이 조용히 바뀐다. 기본
폴백이 LIBERO 라 대개 우연히 맞지만 그건 안전이 아니라 운이라, `register_dataset.py`
가 `constants.py` 에 값을 못 박고 학습 전 `assert (7, 8, 8)` 로 확인한다.

### 3-3. SFT 결과

**teacher forcing 지표에서 베이스 대비 명확히 학습됐다.**

| | 베이스 openvla-7b | SFT |
|---|---|---|
| dx 상관 | 0.048 | **0.448** |
| 그리퍼 상관 | 0.457 | **0.811** |

**롤아웃 성공률 15.6%** (352 에피소드, `eval_base` 홀드아웃).

남은 관찰: 회전 차원의 예측 std 가 정답의 2.4배로 **과분산**이다. 학습 부족이면 보통
평균으로 수축하는데 반대 방향이라, 데이터 다중성(같은 화면에 여러 정답)을 의심한다.
15k/17.5k/20k 지표가 평평하지만 셋 다 LR 감쇠(13,333) 이후 구간이라 정체의 증거로는
쓸 수 없다.

## 4. Phase 3 — RFT (GRPO)

### 4-1. 왜 GRPO 인가

**GRPO (Group Relative Policy Optimization)** 를 썼다. critic 없이 같은 초기 상태에서
G개 궤적을 굴려 **그룹 내 보상을 정규화**한 값을 어드밴티지로 쓴다.

- **critic-free.** 7B 정책 옆에 value network 를 또 얹을 VRAM·시간이 없다.
- **sparse 0/1 보상에 잘 맞는다.** SimpleVLA-RL 의 검증된 성과(LIBERO-Long 97.6,
  데모 1개 SFT 에서 17.3 → 91.7)가 전부 이 설정이다.
- 거리 기반 shaping 을 섞으면 그 레시피에서 벗어나면서 보상 해킹(목표 근처를 맴돌며
  shaping 만 챙기는 행동)의 여지가 생긴다.

**PPO inner epoch = 2.** 처음엔 1이었는데, inner epoch 이 1이면 π_new = π_old 라
**ratio ≡ 1 이 되어 클리핑이 아무것도 하지 않고 사실상 REINFORCE 와 동치**가 된다.
2로 올려 트러스트 리전이 실제로 작동하게 했다 (실측 `ratio_max` 1.6~2.1,
`clip_frac` 8~10% — 클리핑이 살아 있다는 증거).

### 4-2. 프로세스 분리 아키텍처

```
env_isaaclab (Isaac Sim 5.1 + torch 2.7.0+cu128)   ← 롤아웃 워커
        ↕  rft/ipc_bridge.py  (stdout 길이 접두어 프로토콜)
env_eval     (transformers 4.40.1 + timm 0.9.16)   ← 정책 추론/학습
```

openvla-oft 를 제대로 설치하면 torch 2.2.0 을 끌고 와 Isaac Sim 이 고정한 2.7.0 을
깬다. 한 프로세스에 담을 수 없어 venv 2개로 쪼개고 IPC 로 이었다.

### 4-3. 보상 설계

**단계형 sparse 보상.** outcome-only 는 성공률이 0 에 가까울 때 그룹 내 표준편차가 0
이 되어 **전 그룹이 무신호**가 된다.

| 단계 | 보상 | 술어 |
|---|---|---|
| 파지 | 0.2 | `target_grasped` + 블록 5mm 이상 뜸 + **연속 4스텝 유지** |
| 리프트 | 0.4 | 쥔 채 22mm 이상 |
| 트레이 진입 | 0.7 | `block_in_tray` + 정지 + **리프트 이력 필수** |
| 성공 | 1.0 | **16스텝(2초) 유지** |

**각 이벤트는 래치라 에피소드당 한 번만 켜지고, 보상은 최댓값 하나다** (`torch.maximum`
체인). 누적이 아니므로 같은 이벤트를 반복 수확할 수 없다.

**막아 둔 보상 해킹 3종**

1. **파지가 거의 공짜였다.** `target_grasped` 는 거리 60mm + 그리퍼 폭 60mm 면 참이라
   **닫힌 빈 손이 옆을 지나가기만 해도** 켜진다. "블록 5mm 이상 뜸" + "연속 4스텝" 을
   추가하니 파지율이 60% → 15% 로 떨어졌다. 대부분 허위였다.
2. **끌어서 밀어넣기.** 트레이 크레딧에 리프트 래치를 AND 로 걸어 막았다.
3. **튕겨 지나가기.** 블록 최고높이 286mm 가 관측됐다(던지는 동작). 정지 조건을 AND 로
   걸어 안착한 경우만 인정한다.

**패널티는 넣지 않았다.** "파지 후 놓치면 감점" 은 파지 보상 0.2 보다 큰 벌점이면
**아예 안 잡는 쪽이 이득**이 되어 정책이 블록을 회피한다. 재파지는 정상적인 복구
행동이라 억제하면 안 된다. 인정 조건만 엄격히 하는 방향으로 갔다.

### 4-4. 커리큘럼 — 성공률 기반 어닐링

원래 분포에서 트레이 진입이 0/40 인데 커리큘럼 초기 상태(타깃 블록만 트레이 앞으로)
에서는 1/2 였다. 신호를 만들려면 커리큘럼이 필요했다.

다만 **고정 혼합비는 커리큘럼이 아니라 "리셋 분포를 넓혀 둔 것"에 가깝다.** reverse
curriculum(Florensa et al. 2017) 계열의 동력은 쉬운 상태로 신호를 만든 뒤 **원래
분포로 되돌리는** 데 있다. 되돌리지 않으면 커리큘럼 분포에서만 잘하고 목표 분포로의
전이가 보장되지 않는다.

```yaml
bank_stages: [train_c30, train_c20, train_c10, train]   # 커리큘럼 30→20→10→0%
promote_eval_success: 0.30      # 홀드아웃 성공률이 넘으면 승급
promote_deadline_steps: 0       # ★ 데드라인 없음
```

승급을 **스텝 기준에서 성공률 기준으로** 바꿨다. 처음엔 "임계 미달이어도 N스텝 뒤
강제 승급"하는 데드라인을 뒀는데, 이는 방법론적으로 틀렸다 — 성공률을 못 넘겼다는
것은 아직 그 단계를 못 푼다는 뜻이고, 그때는 **커리큘럼을 유지해야** 한다. 문헌의
표준(GoalGAN, ADR 포함)도 데드라인 없는 성능 게이팅이다. 제거했다.

> **함정: 커리큘럼 뱅크가 실제로는 100% 커리큘럼으로 소비되고 있었다.**
> `sample_bank` 는 커리큘럼 행을 앞쪽에 몰아 넣는데(`k < n_curriculum`) 학습은 커서 0
> 부터 순차 순회한다. `train_mix` 는 인덱스 0~1228 이 전부 커리큘럼이라, 실제 소비
> 구간이 통째로 커리큘럼이었다. 30% 라고 믿은 값이 실제로는 100% 였다.
> → `train_c30/c20/c10` 을 새로 만들고 **행 순서를 셔플**했다. 실측으로 소비
> 구간(0~400행)에서 27.5 / 16.2 / 9.2% 를 확인했다.

### 4-5. 최종 학습 설정

`rft/configs/grpo_batched.yaml` (RTX 6000 PRO Blackwell 96GB)

| 항목 | 값 |
|---|---|
| `group_size` | 8 |
| `groups_per_step` | 6 → **업데이트당 48 궤적** |
| `max_group_attempts` | 12 (무신호 그룹 재시도 여유) |
| `dynamic_sampling` | true (표준편차 0 인 그룹 폐기) |
| `max_steps_per_episode` | 300 |
| `temperature` | 1.2 (샘플링·log-prob 양쪽에 적용) |
| `learning_rate` | 2.0e-5 |
| `clip_eps` / `clip_eps_high` | 0.2 / 0.28 (비대칭, DAPO 계열) |
| `kl_coef` | 0.0 |
| `ppo_epochs` | 2 |
| LoRA | r=32, alpha=16 |
| `policy_batch_size` | 8 |
| 평가/저장 | 10 스텝마다, 32 에피소드 (`eval_base` 전용) |

**LoRA 를 두 겹으로 쌓지 않았다.** SFT LoRA 를 `merge_and_unload()` 로 베이스에 병합한
뒤 새 LoRA 를 붙인다. SimpleVLA-RL 도 stock OFT 병합 체크포인트를 받아 RL 을 건다.

**평가는 반드시 `eval_base`(원래 분포 홀드아웃)로만 한다.** 커리큘럼 성능이 올라도
원래 분포에서 떨어지면 의미가 없다.

### 4-6. 정책 forward 배치화

SimpleVLA-RL 과 비교하면 격차가 한 곳에 몰려 있었다.

| | SimpleVLA-RL | 초기 우리 |
|---|---|---|
| `group_size` | 8 | 8 (동일) |
| **업데이트당 궤적** | **512** | **16** (32×) |
| GPU | 8×A800 | 1 |

그런데 `groups_per_step` 을 늘려도 VRAM 은 늘지 않았다 — 정책 forward 가 **샘플 1개씩
순차로** 돌고 있었기 때문이다 (96GB 중 35GB 만 사용). 남는 61GB 는 "여유"가 아니라
**놀고 있는 것**이었고, 그룹을 2배로 늘리면 순차 forward 횟수만 2배가 되어 시간만
2배 들었다.

조사 결과 걸림돌은 모델이 아니라 **호출부 4곳**이었다. `modeling_prismatic.py` 의
멀티모달 `forward()` 는 설계상 배치 전제이고, B>1 을 막는 두 곳(KV캐시 생성,
`prepare_inputs_for_generation`)은 `generate()` 경로라 RFT 와 무관했다.

`action_logits()` 를 배치 함수로 바꾸고 호출부 루프를 제거했다. 함께 넣은 안전장치:

**프롬프트 길이 균일성 검사.** 슬라이스 시작 위치가 스칼라라, 행마다 길이가 다르면
**에러 없이 정책 분포만 조용히 달라진다.** 체크포인트 토크나이저 실측으로 학습 경로
프롬프트가 전부 22토큰임을 확인했지만(`INSTRUCTION_TEMPLATES_EVAL` 중 하나만 24토큰),
가정이 깨지는 순간 즉시 에러를 내도록 `attention_mask.sum(-1)` 을 검사한다.

**벤치마크 실측** (`scripts/bench_policy_batch.py`)

| 배치 | no_grad 처리량 | grad 처리량 | grad peak VRAM |
|---|---|---|---|
| 8 | **2.57×** | **2.87×** | 32.6 GB |
| 16 | 포화 (이득 없음) | | |

→ `policy_batch_size=8`, `groups_per_step=6` 으로 확정. 업데이트당 궤적 16 → 48
(SimpleVLA 대비 1/32 → 1/10).

**배치 ↔ 순차 동치 시험**을 `--verify-checkpoint` 에 회귀 테스트로 넣었다. 처음엔
토큰 완전일치를 요구했다가 실패했는데, 진단해 보니 top1-top2 격차 대비 무시할 수준의
**bf16 수치오차**(로짓 절대차 ~0.2)였다. 슬라이스 오류라면 O(10) 이 나온다. 판정을
로짓 수준(`TOL=1.0`)으로 바꿔, bf16 노이즈는 통과하되 실제 슬라이스 버그는 잡도록 했다.

## 6. 검증 및 방법론

### 6-1. 가장 중요한 발견 — 성공 판정이 "스침"을 세고 있었다

`success_bonus` 가 `placed_signal()` 의 **순간값**을 돌려주고 있었다. 그런데 종료 조건
`task_success()` 는 같은 술어가 16스텝 연속일 때만 참이다. **두 정의가 갈라져 있어서**,
`settled` 임계가 0.03 m/s 인 탓에 블록이 트레이 영역을 느리게 **스치기만 해도** 보상이
1 로 뜨고 성공으로 집계됐다.

발견 경로는 지표가 아니라 **롤아웃 영상 육안 확인**이었다. 영상에 트레이로 들어가는
장면이 하나도 없는데 성공률이 20.3% 로 보고되고 있었다.

증명은 프레임 수로 했다. SFT 12 에피소드에서 `diag["success"]` 는 2건을 잡았지만
**12개 전부 300스텝을 완주**했다 — 즉 `task_success` 종료가 한 번도 발동하지 않았고
실제 안착은 0건이었다.

```python
def success_bonus(env, robot_cfg=..., ee_frame_cfg=...):
    from .terminations import task_success
    return task_success(env, robot_cfg=robot_cfg, ee_frame_cfg=ee_frame_cfg).float()
```

이제 보상·종료·평가가 한 정의를 읽는다. **파급이 컸다** — 그 전까지의 "SFT 기준선
20.3%" 를 포함해 이 지표에 근거한 모든 판단이 무효화됐고, 실험 계획을 다시 세웠다.
그 상태로 RFT 를 계속 돌렸다면 "안착"이 아니라 "스침"을 강화했을 것이다.

### 6-2. 정책 경로 검증

`--verify-checkpoint` 는 우리 샘플링 경로(parallel decoding, 56 액션 토큰 1회 forward)가
모델의 `predict_action` 과 같은 액션을 내는지 확인한다. **실측 차이 7.8e-08.** 이게
어긋나면 증상은 "커브가 안 오른다" 하나로만 드러난다.

구현 과정에서 `predict_action` 의 3단계 프로토콜(29871 토큰 삽입, labels 준비, 액션
마스크)을 처음엔 일부 누락했고, 이 검증이 잡아냈다.

### 6-3. 통계적 유의성

물리 시뮬레이션이 결정론적이지 않아 **같은 체크포인트·같은 조건에서 파지율이 5.0 /
7.5 / 15.0% 로 흔들렸다.** 40 에피소드 단일 측정으로 RFT 전후를 비교하면 안 된다는
뜻이다 — "파지율이 5%→15% 로 올랐다"는 이 편차 안에 완전히 묻힌다.

그래서 표본을 32 → 104 → 352 로 단계적으로 키웠다. 최종 판정:

```
SFT  15.6%  (n=352)
RFT  19.9%  (n=352)
차이 +4.3%p,  SE = 2.88%p  →  1.48 SE   (유의하지 않음)
유의 판정에 필요한 표본: 조건당 약 650 에피소드
```

**결론을 "RFT 가 개선했다"로 쓰지 않는다.** 관측된 차이는 개선 방향이지만 현재
표본으로는 시뮬레이션 편차와 구분되지 않는다.

### 6-4. 베이스 모델 비교

처음엔 "OFT 인터페이스가 없어 베이스 평가는 불가능"하다고 판단했으나 이는 틀렸다 —
`eval_rollout.py` 는 범용 `predict_action` 을 쓰고 `embed_norm_stats.py` 도 이미 있었다.
`--adapter`(LoRA 를 베이스 위에 로드)와 `--chunk-len`(베이스는 1스텝 액션) 옵션을
추가해 **동일 시뮬레이션 환경·동일 로봇 플랫폼**에서 측정했다.

시각 도메인·태스크·제어 규약이 베이스와 맞지 않는다는 점은 비교의 결함이 아니라
**측정하려는 대상 그 자체다** — 그것들을 맞추는 것이 SFT 의 목적이기 때문이다.
따라서 이 비교는 "SFT 가 기여했는가"에 유효한 근거다 (단, "OpenVLA 가 이 태스크를
못한다"는 일반적 주장의 근거는 아니다).

### 6-5. 회귀 테스트

`--self-check`(GPU 불필요)와 `--verify-checkpoint`(GPU 필요)로 나눴다. 전자에는
`maybe_promote` 승급 시나리오, `bank_for_step` 등 순수 로직을, 후자에는 정책 경로
동치 시험을 넣었다.

한 번은 메서드를 `__init__` **중간에** 삽입해 크래시를 냈다. 이후 소스를 직접 검사하는
검사를 추가했다.

## 7. 조용히 실패한 함정들

전부 실제로 당했고, **증상은 예외 없이 "성공률 0" 하나로만 나타났다.**

| 함정 | 증상 | 해결 |
|---|---|---|
| `success_bonus` 순간값 | 스침을 성공으로 집계 (§6-1) | `task_success` 참조 |
| `success_latch |= reward > 0.5` | 성공이 **영원히** 안 잡힘. `RewardManager` 는 `func × weight × dt` = 0.125 를 돌려준다 | `> 1e-6` (부호만 판정) |
| `ppo_epochs=1` | ratio≡1, 클리핑 무력화 | 2로 상향 |
| `train_mix` 정렬 | 30% 로 믿은 값이 실제 100% | 셔플된 뱅크 재생성 |
| YAML `~` 미확장 | 워커 실행 실패 | `.expanduser()` |
| **YAML 오타가 조용히 무시됨** | 키를 틀리면 기본값으로 돌아가는데 알 방법이 없다 | 미해결 — `extra` 에 담기고 경고 없음 |
| `detect_robot_platform` | 경로 이름이 학습 차원을 바꿈 | `constants.py` 고정 + assert |
| `VLA_DECIMATION` 누락 | 정책이 3배 빠르게 움직임 | 기본값 15 로 통일 |
| 그리퍼 부호 역전 | "닫아라"에 열림 → 파지 불가 | `GRIPPER_INVERT_FOR_VLA=False` |
| `predict_action(do_sample=…)` | `**kwargs` 로 **조용히 삼켜짐** | 인자 제거 |
| 단계형 보상 켜고 성공률 보고 | `reward` 평균(0.2/0.4)을 성공률로 오독 | `diag["success"]` 에서 읽음 |
| EULA 프롬프트가 stdout 오염 | IPC 프로토콜 파손 | fd 보호를 `parse_args()` 앞으로 |
| `max_group_attempts` 미조정 | `groups_per_step` 만 6으로 올려 배치 미달 | 12로 (2배 여유) |
| 로그 버퍼링 | 크래시 시 결과 통째 유실 | `python -u` |

## 8. 왜 성공률이 높은 수준에 도달하지 못했는가

0% → 15.6% → 19.9% 는 방향은 맞지만 절대 수준이 낮다. 원인을 실측 근거가 있는 것과
가설에 머무는 것으로 나눠 정리한다.

### 8-1. 단계 도달률 — 병목은 "리프트 → 트레이 진입" 구간

성공은 4단계 연쇄다. run3 의 마지막 20스텝 롤아웃 평균:

| 단계 | 도달률 | 직전 단계 대비 통과율 |
|---|---|---|
| 파지 | 43.4% | **43%** ← 첫 번째 큰 손실 |
| 리프트 | 49.6% | (파지 판정보다 관대해 역전) |
| 트레이 진입 | 21.2% | **43%** ← 두 번째 큰 손실 |
| 성공 (2초 유지) | 20.5% | 97% |

읽히는 것이 두 가지다.

**(a) 진입에 성공하면 거의 유지된다** (21.2% → 20.5%, 통과율 97%). "2초 유지" 조건이
성공률을 깎는 주범이 **아니다.** 판정 엄격성 탓으로 돌릴 수 없다.

**(b) 손실이 파지와 운반 두 곳에 반씩 걸려 있다.** 각 43% 라 곱하면 0.43 × 0.43 ≈ 0.19
로 관측된 최종 성공률과 맞는다. **한 곳을 고쳐도 상한이 43% 다** — 곱셈적 감쇠 구조라
어느 한 단계의 개선만으로는 높은 성공률에 도달할 수 없다.

### 8-2. 회전 차원의 과분산 — 파지 실패의 유력한 원인

SFT 정책의 회전 예측 std 가 정답의 **2.4배**다. 학습 부족이면 보통 평균으로 수축하는데
반대 방향이라 단순한 학습량 문제가 아니다. 롤아웃의 `yaw_err` 도 학습 내내 0.6~0.95
rad (35~55°) 에서 내려오지 않았다.

원인으로 의심하는 것은 **정답의 다중성**이다. 블록은 60×30×30 mm 직육면체로
`BLOCK_SYMMETRY_ORDER = 2` — yaw 가 θ 든 θ+π 든 물리적으로 같은 파지다. 초기 yaw 는
±π 무작위다. 즉 **같은 화면에 두 개의 옳은 정답이 있고**, 회귀식으로 학습하면 정책이
그 둘 사이에서 갈라진다. 30mm 폭 블록을 80mm 그리퍼로 잡는 데 35~55° 오차는 치명적이다.

이것이 사실이라면 데이터를 늘리거나 오래 학습해도 해결되지 않는다. **라벨을 대칭
정규화**(yaw 를 [0, π) 로 접기)하는 것이 정공법인데, 이번 예산에서는 시도하지 못했다.
가장 유망한 다음 수순으로 본다.

### 8-3. 데이터의 다양성 상한

1,500 에피소드는 **사람 데모 12개**를 MimicGen 으로 증강한 것이다. MimicGen 은 소스
궤적을 새 물체 배치로 변환·재생하는 방식이라, **소스에 없는 전략은 생성되지 않는다.**
숫자는 1,500 이지만 행동의 다양성은 12개에 가깝다.

실제로 소스를 5 → 12개로 늘렸을 때 수율은 44 → 43% 로 그대로였다 — 소스 확대의 효과가
수율이 아니라 다양성 쪽에 있다는 것은 확인했지만, **다양성이 충분한 수준인지는 확인하지
못했다.** SkillGen 이 0% 로 막힌 것(§2-5)도 여기에 겹친다. SkillGen 은 모션 플래닝으로
소스에 없는 경로를 만들어 내는 경로였고, 그게 됐다면 이 상한이 완화됐을 것이다.

### 8-4. RFT 예산이 두 자릿수 배 부족했다

| | SimpleVLA-RL | 이 프로젝트 (run3) |
|---|---|---|
| 업데이트당 궤적 | 512 | 16 |
| 업데이트 수 | 수백~ | 105 |
| **총 궤적** | **10⁵~10⁶** | **약 1,700** |
| GPU | 8×A800 | 1 |

SimpleVLA-RL 의 17.3 → 91.7 은 이 규모에서 나온 값이다. 우리는 **총 롤아웃 궤적 수가
2~3 오더 작다.** 배치 확대(§4-6)로 격차를 32× → 10× 로 줄였지만 총량은 여전히 부족하고,
run6 이 커리큘럼 승급 임계를 한 번도 넘지 못한 것도 같은 제약의 다른 얼굴이다.

RL 의 개선폭이 유의성에 못 미친 것은 알고리즘 선택보다 **예산**으로 설명하는 편이
근거에 맞다. 다만 이는 "더 돌리면 오른다"의 증명이 아니라, **현재 데이터로는 판정할 수
없다**는 뜻이다.

### 8-5. 관측이 단일 RGB 뷰이고 proprio 가 없다

`num_images_in_input=1`, `use_proprio=False`, 224×224 정면 뷰 하나다. 손목 카메라도
관절 상태도 없다. 깊이와 그리퍼-블록 상대 자세를 단일 뷰에서 추정해야 하는데, 이는
파지 정밀도(§8-2)에 직접 불리하다. OFT 는 손목 뷰 추가와 proprio 를 모두 지원하므로
**설정으로 해결 가능한 항목**이지만, 데이터를 다시 만들어야 해서 손대지 않았다.

### 8-6. 학습량 — 근거가 불충분한 항목

SFT 20,000 스텝은 약 1.07 에폭이다. 15k / 17.5k / 20k 체크포인트 지표가 평평해 수렴한
것처럼 보이지만, **셋 다 LR 감쇠(13,333) 이후 구간이라 정체의 증거가 되지 못한다.**
감쇠 후에는 지표가 평평해지는 것이 정상이기 때문이다. 학습량이 충분했는지 부족했는지
**이 실험 설계로는 판정할 수 없다.** 재학습한다면 감쇠 이전 체크포인트를 반드시
남겨야 한다.

### 8-7. 종합

성공률이 낮게 머문 이유를 하나로 지목한다면 **파지 정밀도(§8-2)** 다. 단계 도달률이
가리키는 첫 병목이고, 회전 과분산이라는 독립적 증거가 같은 곳을 가리키며, 원인 가설
(라벨 대칭 다중성)이 구체적이고 검증 가능하다. 그 위에 데이터 다양성 상한(§8-3)과
RFT 예산 부족(§8-4)이 얹혀 개선 여지를 좁혔다.

반대로, **성공 판정의 엄격성이나 태스크 난이도로 돌리는 설명은 근거가 약하다** —
진입 후 유지 통과율이 97% 이기 때문이다.

## 9. 결론

**확인된 것**

1. **SFT 는 명확히 기여했다.** 0% → 15.6%. 사전학습 정책이 한 번도 완수하지 못한
   태스크를 성립시켰고, teacher forcing 지표(dx 상관 0.048→0.448)도 같은 방향이다.
2. **파이프라인 전체가 동작한다.** 텔레옵 20개 → MimicGen 1,500개 → RLDS → SFT →
   Isaac Sim 인루프 GRPO 까지, 세 venv·두 프로세스에 걸쳐 끝까지 이어진다.
3. **측정 인프라의 정확성이 실험 자체보다 중요했다.** 성공 판정 버그 하나가 며칠치
   실험 해석을 무효화했고, 그것을 잡은 것은 집계 지표가 아니라 원시 롤아웃 영상이었다.

**확인되지 않은 것**

1. **RFT 의 개선은 유의하지 않다** (+4.3%p, 1.48 SE). 방향은 긍정적이지만 현재 표본
   으로는 시뮬레이션 편차와 구분되지 않는다.
2. **커리큘럼의 전이 효과는 미확정.** 최종 실행(run6)은 승급 임계를 넘지 못해 원래
   분포 구간에 도달하지 못했다.
3. **배치 확대 가설은 기각됐다.** 48궤적이 16궤적보다 낫지 않았다.

**남은 부채**

- `TRAY_INNER_SIZE` 2.0× 완화 — 트레이 형상을 바꾸므로 학습 데이터 대비 OOD 다.
  형상은 원복하고 성공 판정만 근접 기반으로 바꾸는 쪽이 깨끗하다.
- SkillGen 0% (§2-5), IK 도달성 가설 미검증.
- 워커에 스텝 타임아웃이 없어 Isaac Sim assertion 시 무한 정지한다.
- SFT 스텝 연장의 가치 미확정 — 15k/17.5k/20k 가 평평하지만 전부 LR 감쇠 이후 구간
  이라 정체의 증거가 못 된다. 재학습한다면 **감쇠 이전 체크포인트를 반드시 남길 것.**
- 유의성 확보에는 조건당 약 650 에피소드가 필요하다 (조건당 약 70분).
